> **An Agent Application is a software system whose primary unit of execution
> is one or more persistent, tool-using agents operating in durable workspaces
> to accomplish work over time and produce or maintain durable artifacts.**

ChatGPT, Claude, OpenClaw, Lovable, and Replit Agent have different interfaces
and do different jobs. Underneath, each gives a persistent agent a place to
work, tools it can use, and state it can return to later. This paper calls the
whole product an Agent Application.

Keeping an agent's work changes the application lifecycle. Developers need to
decide how to structure and package the project, where each instance keeps its
state, who may use that state, how updates reach existing instances, and how to
price the running product.

| Era | Application model | What persisted |
|---|---|---|
| Personal computing | Desktop application | Local files, installers, the OS |
| Internet | Web application | Servers, databases, the URL |
| Mobile | Mobile application | Device identity, sensors, the store |
| Agent computing | **Agent Application** | Instances, workspaces, durable work, lineage |

## What makes it an Agent Application

The interface does not define the category. The execution model does. Four
properties distinguish an Agent Application from a model endpoint, a stateless
chatbot, or a fixed workflow:

| Property | What it looks like |
|---|---|
| Persistent agent instance | A new message or event returns to the same agent, privacy domain, and ongoing work |
| Agent-directed control flow | The agent reads the current state and chooses its next action within application guardrails |
| Durable computational workspace | Files, instructions, memory, code, and other working state remain available to later runs |
| Durable work | Artifacts, workspace state, external records, or continuing processes outlive the event that created them |

A workspace defines a logical boundary for durable state. A platform may store
that state in databases, object storage, or retained sessions. In the canonical
design, each instance gets an isolated persistent virtual filesystem that the
platform restores on demand. The agent can read everything in its workspace.
The people, records, and work that can safely share that workspace form its
**privacy domain**.

[ChatGPT](https://help.openai.com/en/articles/20001275-chatgpt-work-and-codex),
[Claude](https://support.claude.com/en/articles/14116274-organize-your-tasks-with-projects-in-claude-cowork),
[Gemini](https://support.google.com/gemini/answer/17094507),
[Lovable](https://docs.lovable.dev/features/agent-mode),
[Replit Agent](https://docs.replit.com/features/version-control/checkpoints-and-rollbacks),
[OpenClaw](https://docs.openclaw.ai/start/openclaw), and
[Lightfield](https://docs.lightfield.app/) already organize ongoing work this
way. Depending on the product, an instance belongs to a user, project, personal
agent, company workspace, or customer relationship.

## Where Agent Applications appear

The **agent widget** is the most common interface today. An Agent Application
may instead appear through an API, a communication channel, or an event that
starts work without opening a conversation.

The widget may fill the screen, sit beside another application, or open in a
popup. It handles authentication and session switching. Users can choose models
and harness options, type or talk, upload files, and control the running agent.

The conversation view shows messages alongside progress, reasoning summaries,
tool calls, and approvals. It also reports errors and other runtime events. The
widget renders artifacts and interactive UI returned by the agent. [OpenAI
ChatKit](https://openai.github.io/chatkit-js/),
[CopilotKit](https://docs.copilotkit.ai/), and [AI SDK
Elements](https://elements.ai-sdk.dev/examples/chatbot) package many of these
parts. [AG-UI](https://docs.ag-ui.com/) defines the event stream between an
agent and its frontend. [MCP Apps](https://modelcontextprotocol.io/extensions/apps/overview)
lets tools place forms, dashboards, viewers, and other interactive controls
inside the conversation.

## How the pieces fit together

By 1994, web applications were beginning to emerge from a few basic pieces.
HTTP moved requests, HTML described pages, and browsers displayed them.
JavaScript later added behavior. Frameworks gave developers a repeatable way to
assemble those pieces into applications.

Agent developers are working with a similar collection of parts. The Model
Context Protocol connects agents to tools. Reusable instructions can travel as
Agent Skills, while Agent Plugins package skills and MCP server configurations.
Sandboxed compute gives agents a place to run code and work with files. A
harness runs the agent loop around the model.

A harness becomes an [Agent Application framework](/concepts/framework) as it
takes on more of the development and operating lifecycle: project structure,
local tools, evaluations, packaging, deployment, and the production runtime.
The framework still keeps its own programming model and native project layout.

## Agent Application Programming

Agent Application Programming starts with a use case and decides where each
part of the work belongs. Some behavior belongs in conventional code; other
behavior belongs in instructions, skills, tools, hooks, specialist agents,
dynamic workflows, state, or policy. The design also determines which
transitions code guarantees and which ones the model chooses while it works.

The paper calls this discipline **Agent Application Programming**. It includes
the design of dependencies, permissions, evaluations, observability, and cost
controls around the agent. AI coding agents are likely to do much of this work.
They can inspect a project and propose a decomposition, then write code and
natural-language programs, run evaluations, and revise the design from the
results. Humans still set the goals, authority, risk limits, and acceptance
criteria. [Section 8.7 of the
paper](/paper#8-7-agent-application-programming) develops the idea.

## From an agent project to running instances

A developer writes an **agent project** in the native layout of a harness /
Agent Application framework. When the project is ready, the publisher creates a
fixed release using the framework's own build and release process. An
[Agent Application Platform](/concepts/platform) runs the native project rather
than translating every framework into one generic schema.

```text
account-operator/
|-- agent-program
|-- instructions-and-knowledge
|-- tools-and-integrations
|-- agents-and-workflows
|-- state-and-workspace
|-- interfaces-and-artifacts
|-- triggers-and-background-work
|-- policy-and-approvals
|-- evaluations-and-observability
`-- application-lifecycle
```

The names in this diagram describe responsibilities, not folders. A framework
may implement them in code, Markdown, configuration files, platform settings,
or a mixture of these. Standards apply where the application meets another
system. MCP connects tools and data. Agent Skills is a format for reusable
instructions. The Agent Plugins format bundles skills with MCP configuration.
AG-UI connects agent backends to frontends, and A2A connects independently
deployed agents.
[Section 9 of the paper](/paper#9-the-agent-project-and-capability-model) explains
the model and compares current frameworks.

An application may create an instance for a user, team, customer, project,
ticket, or another continuing relationship. Each instance accumulates its own
workspace, artifacts, instructions, and history. Instances diverge as they
work, so updating a fleet involves more than copying the same release over each
one.
