## From contracts to standards

The paper points to several areas where an open contract may eventually help.
Standards work should start when two or more independent implementations need
to exchange the same information across a stable boundary.

The capability model serves a different purpose. It lists the parts of an
Agent Application so developers can compare frameworks and framework authors
can see what developers may need. It does not prescribe project files, APIs,
builds, or release artifacts.

Likely candidates for future standards include:

1. **Agent Artifact contract.** This would cover identity, content and state,
   provenance, permissions, versions, rendering, and actions. See
   [Agent Artifact](/concepts/artifact) for the two-layer model.
2. **Workspace and lineage export.** This would carry portable state and its
   release and overlay history, using secret references instead of credentials.
3. **Agent identity and delegated authority.** This work comes later, after
   principal and cross-system authority models are mature enough to support a
   shared abstraction.

A proposal should identify the independent implementations that need to
exchange information and the exact problem they face. Its scope should stop at
that boundary rather than trying to normalize each framework's project model.
