---
title: "Agent Project"
description: "The harness- or framework-native source directory used to create Agent Application releases."
---

> An **Agent Project** is the source directory for an Agent Application, in the
> layout expected by its harness or framework. It contains the code,
> instructions, configuration, dependencies, and tests used to create a
> release.

An agent project keeps the layout prescribed by its harness or framework. A
Claude Code project, for example, may use `CLAUDE.md`, `.claude/`, and
`.mcp.json`. Other frameworks have their own files and conventions. The project
stays in that native form when it moves from local development to production.

Agent Projects do not share a standard directory structure. They may contain a
primary agent program, instructions, tools, workflows, state, interfaces,
artifacts, triggers, policy, evaluations, and operational configuration.
Section 9 groups these parts into a capability model so developers can compare
frameworks. The model does not define a portable project schema, and most
projects will use only part of it.

An [Agent Application framework](/concepts/framework) ties the project to the
rest of the development process. It defines how developers run and test the
project locally, package it, deploy it, and use it in production. It may also
tell an [Agent Application Platform](/concepts/platform) which models, tools,
workspace features, permissions, schedules, artifact support, and upgrade
behavior the project needs.

Plugins are project dependencies. They can add skills, MCP servers, hooks, or
other components. Each framework decides how to install and record them. When a
publisher creates a release, the framework and platform record the project
source, its dependencies, the runtime, and the tests in their native release
format.

Developers will usually say they are "building an agent." The term *agent
project* becomes useful when the source directory must be distinguished from an
[instance](/concepts/instance), a session, or the runtime agent doing the work.

See [the paper](/paper), sections 7, 9, and 10. Appendix A shows one
non-normative project layout.
