# Hello World: a durable notebook

The smallest useful Agent Application can return to work it saved during an
earlier run. A one-shot task runner cannot.

This example is a notebook agent for one user. It saves notes in its workspace
and maintains a short briefing that the user can open without reading through
the conversation. The declarations below are harness-neutral conceptual
pseudocode. A framework profile maps the same roles to real native files and
APIs.

```text
durable-notebook/
|-- instructions.md
|-- tools/
|   `-- save-note.ts
|-- evals/
|   `-- persistence.yaml
`-- agentapplication.yaml
```

## The program

`instructions.md` contains the behavior written in natural language:

```markdown
You maintain a research notebook for one user.

When the user asks you to remember something, append it to notes.md with the
date and source. When asked for a briefing, read notes.md and update briefing.md.
Never remove an earlier note unless the user asks you to.
```

`save-note.ts` provides the deterministic file operation:

```ts
import { appendFile } from "node:fs/promises";

export async function saveNote(text: string) {
  await appendFile("notes.md", `- ${new Date().toISOString()}: ${text}\n`);
  return { saved: "notes.md" };
}
```

The application manifest binds the root instructions and tool implementation to
the runtime. It also asks for a persistent workspace and uses the user ID as the
instance key:

```yaml
apiVersion: agentapplication.io/v0alpha1
kind: AgentApplication

metadata:
  name: durable-notebook
  version: 0.1.0

runtime:
  profile: conceptual/reference-0
  entrypoint: instructions.md
  requiredFeatures:
    - fs.persistent
    - tool.calling

tools:
  - name: save_note
    description: Append a dated note to the current instance's notebook.
    inputSchema:
      type: object
      required: [text]
      properties:
        text:
          type: string
    implementation: tools/save-note.ts#saveNote

instance:
  privacyDomain: user
  key: user.id

workspace:
  version: 1
  durability: required
  isolation: per-instance
  backgroundExecution: denied

artifacts:
  - type: briefing
    path: briefing.md

evals:
  behavior: evals/
```

The persistence evaluation runs two sessions against the same instance and one
against a different instance:

```yaml
name: notes survive suspension
steps:
  - run:
      instance: ada
      input: Remember that the launch moved to September 18.
  - suspend: ada
  - run:
      instance: ada
      input: Prepare a launch briefing.
  - run:
      instance: bea
      input: Prepare a launch briefing.
assert:
  - workspace: ada
    fileContains:
      notes.md: September 18
      briefing.md: September 18
  - workspace: bea
    fileAbsent: notes.md
```

A runnable framework implementation replaces the conceptual profile and binding
syntax with its native entrypoint, tool registration, and evaluation API. The
application-level requirements stay the same.

## Two runs, one continuing instance

On Monday, Ada says, "Remember that the launch moved to September 18." The
platform routes the request to Ada's notebook instance. The agent writes the
fact to `notes.md`, then the runtime suspends.

On Friday, Ada asks for a launch briefing. The platform wakes the same instance
and restores its workspace. The agent reads Monday's note and writes
`briefing.md`. Ada can open that file directly, share it, or return next week and
ask the agent to revise it.

| Defining property | Where it appears |
|---|---|
| Persistent agent instance | Ada's stable instance key selects the same notebook on every run and keeps it separate from other users |
| Durable computational workspace | `notes.md`, `briefing.md`, and the agent's instructions survive suspension |
| Durable work | The notes and briefing outlive the conversations that created them |

## The same notebook with a plugin

A plugin is optional. The smallest example keeps `save-note.ts` in the project
to show the full application without an external dependency. A second version
can take the note tool and briefing procedure from a portable plugin:

```text
durable-notebook/
|-- <harness-native entrypoint>
|-- instructions.md
|-- evals/
|   `-- persistence.yaml
|-- agentapplication.yaml
`-- agentapplication.lock
```

The application manifest declares intent and selects the components it needs:

```yaml
dependencies:
  plugins:
    - name: research-notebook-tools
      specification: agent-plugins/1.0.0
      source:
        type: git
        url: https://example.com/research-notebook-tools.git
      requirement: "^1.0.0"
      required: true

activation:
  components:
    - research-notebook-tools/mcp/save-note
    - research-notebook-tools/skill/briefing
```

The release builder resolves that requirement and writes the exact content to
the lockfile:

```yaml
lockVersion: 1
plugins:
  research-notebook-tools:
    version: 1.0.2
    source: https://example.com/research-notebook-tools.git
    revision: 7ad31bc
    digest: sha256:82e1...
    specification: agent-plugins/1.0.0
    components:
      skills:
        - briefing
      mcpServers:
        - save-note
    active:
      - research-notebook-tools/mcp/save-note
      - research-notebook-tools/skill/briefing
```

The plugin version still needs the same instance rule, workspace contract, and
persistence evaluation. Installing the package does not grant filesystem or
external credentials, and activating its components does not change that rule.

The [Agent Project and Release
Specification](/specifications/agent-project-and-release) defines the manifest,
dependency, activation, and lock contract this example uses.
