# Hello World: a durable notebook

The smallest useful Agent Application can return to work it saved during an
earlier run. A one-shot task runner cannot.

This example is a notebook agent for one user. It saves notes in its workspace
and maintains a short briefing that the user can open without reading through
the conversation. The files below are illustrative. A real implementation uses
the project layout and APIs of its chosen framework.

```text
durable-notebook/
|-- instructions.md
|-- tools/
|   `-- save-note.ts
`-- evals/
    `-- persistence.yaml
```

## The program

`instructions.md` contains the behavior written in natural language:

```markdown
You maintain a research notebook for one user.

When the user asks you to remember something, append it to notes.md with the
date and source. When asked for a briefing, read notes.md and update briefing.md.
Never remove an earlier note unless the user asks you to.
```

`save-note.ts` provides the deterministic file operation:

```ts
import { appendFile } from "node:fs/promises";

export async function saveNote(text: string) {
  await appendFile("notes.md", `- ${new Date().toISOString()}: ${text}\n`);
  return { saved: "notes.md" };
}
```

The framework wires these pieces together. Whatever its API or configuration
looks like, the implementation needs to make these choices:

| Choice | Notebook behavior |
|---|---|
| Primary program | Load `instructions.md` when the notebook agent runs |
| Tool registration | Expose `saveNote` as a `save_note` tool with one string argument |
| Instance routing | Use the authenticated user ID, so Ada and Bea get different instances |
| Workspace | Keep files between sessions and isolate one user's files from another's |
| Artifact | Present `briefing.md` as durable output the user can open |
| Background work | None for this example |

Claude Agent SDK, Google ADK, LangGraph, OpenAI Agents SDK, and Vercel AI SDK
would express this wiring differently. That variation is expected.

The persistence evaluation runs two sessions against the same instance and one
against a different instance:

```yaml
name: notes survive suspension
steps:
  - run:
      instance: ada
      input: Remember that the launch moved to September 18.
  - suspend: ada
  - run:
      instance: ada
      input: Prepare a launch briefing.
  - run:
      instance: bea
      input: Prepare a launch briefing.
assert:
  - workspace: ada
    fileContains:
      notes.md: September 18
      briefing.md: September 18
  - workspace: bea
    fileAbsent: notes.md
```

A runnable implementation uses its framework's native agent definition, tool
registration, state service, and evaluation API. The observable behavior in the
test stays the same.

## Two runs, one continuing instance

On Monday, Ada says, "Remember that the launch moved to September 18." The
platform routes the request to Ada's notebook instance. The agent writes the
fact to `notes.md`, then the runtime suspends.

On Friday, Ada asks for a launch briefing. The platform wakes the same instance
and restores its workspace. The agent reads Monday's note and writes
`briefing.md`. Ada can open that file directly, share it, or return next week and
ask the agent to revise it.

| Defining property | Where it appears |
|---|---|
| Persistent agent instance | Ada's stable instance key selects the same notebook on every run and keeps it separate from other users |
| Durable computational workspace | `notes.md`, `briefing.md`, and the agent's instructions survive suspension |
| Durable work | The notes and briefing outlive the conversations that created them |

## The same notebook with a plugin

A plugin is optional. The smallest example keeps `save-note.ts` in the project
to show the full application without an external dependency. A second version
can take the note tool and briefing procedure from a portable plugin:

```text
research-notebook-tools/
|-- plugin.json
|-- skills/
|   `-- briefing/
|       `-- SKILL.md
`-- mcp.json
```

The plugin uses the [Agent Plugins 1.0](https://agent-plugins.org/specification)
package format. Its skill contains the briefing procedure, while `mcp.json`
describes the server that exposes the note tool. The notebook project installs
and selects those components through its framework's plugin mechanism.

The framework should record the exact plugin version, source, and digest using
its own package or release system. Installation still does not grant filesystem
or external credentials, and activation still does not authorize them. The
plugin version also needs the same instance routing, workspace isolation, and
persistence evaluation as the project-owned tool version.
